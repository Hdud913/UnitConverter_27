## 1) 주제 (한 문장)

meter로 기록된 거리를 feet로 문서에 넣기 전에, **환산 상수를 다시 검색·판단하지 않고** 같은 방식으로 **신뢰 가능한 feet 값**을 얻는 일을 줄인다. **귀찮아서 변환을 포기·대충 넘기는** 경우도 줄인다.

*(솔루션 최소화: “변환 프로그램을 만든다”가 아니라, 구글+계산기+판단·**회피**에 쓰이는 **시간·불확실성**을 줄이는 것이 주제다.)*

---

## 2) R-G-I-O

| 항목 | 내용 |
|------|------|
| **Role** | 길이 단위 변환을 반복하는 **개발자** — 회의록 등 **문서**에 meter 기반 거리를 feet로 적어야 함 |
| **Goal** | **한 번의 입력**으로 meter→feet(및 필요 시 yard) 결과를 얻고, **문서에 붙일 수 있는 문자열**을 확보한다. 상수는 **코드/설정에 고정**되어 매번 구글·계산기·3.28084 vs 3.281 **판단을 하지 않는다** |
| **Input** | `단위:값` 형식 문자열 (예: `meter:2.5`) — 음수·잘못된 형식·미지원 단위는 거부 |
| **Output** | 지원 단위 전부에 대한 변환 결과 (예: `2.5 meter = … feet`) — **일관된 비율**(README: `1 meter = 3.28084 feet`)로 계산된 값; 추후 spec에서 **소수 자릿수·반올림 규칙** 명시 |

## 4) 표면 문제 — 이번 프로젝트에서 **하지 않을 것**

Mom Test **표면 문제**를 그대로 범위로 삼지 않는다.

| 하지 않을 것 | 이유 |
|--------------|------|
| **“단위 변환 프로그램/앱을 만든다”**를 **문제 정의**로 삼기 | 진짜 문제는 **상수 재검색·판단·수동 곱셈·문서 반복**이지, 도구 존재 자체가 아님 |
| **범용 단위 변환기·모든 물리량** (질량, 온도, 환율 등) | 인터뷰 pain은 **길이 meter↔feet** 중심; 범위 확장은 검증 없음 |
| **웹/모바일 UI, 회의록 자동 연동, 구글 대체 검색엔진** | 워크플로 일부만 대체; 이번 과제는 **Python CLI + 품질/테스트** |
| **사용자에게 상수 암기·학습시키기** | 인터뷰이는 **외우지 않음**을 선택 — 암기 UX는 목표 아님 |
| **추가 요구사항 전부를 spec 없이 한꺼번에 구현** | JSON/YAML 설정, 동적 단위 등록, JSON/CSV 출력은 **README 추가 요구** — **spec 확정 후** 단계적 구현 (이번 spec은 **기본 요구 + Mom Test 성공 기준** 우선) |

## 부록: 진짜 문제 & 증거 (참조)

**진짜 문제 (한 문장):**  
meter로 된 거리를 feet로 쓸 때마다 환산 상수를 다시 찾고, 어느 숫자가 맞는지 스스로 판단한 뒤 계산기로 곱해 문서에 넣는 과정이 **귀찮아** **변환을 포기하고 대충 넘긴 적**도 있으며, 변환을 할 때는 **회당 약 1분**이 들고 **한 달에 약 20번** 반복된다.

**Mom Test 증거 4줄:**

1. "지난번에 meter를 feet로 바꿀 때 비율을 매번 구글링했다."
2. "1미터가 몇 feet인지 정확한 숫자가 헷갈렸다. 솔직하게 말하면 어려워서 굳이 외우지 않았다."
3. "지난 한 달 안에 20번 정도, 검색 포함 1분 정도 걸렸다."
4. "아예 변환을 포기하고 대충 넘긴 적이 있다. 귀찮아서 그랬다."

**다음 검증 가설** (`01.REPORT.md` §7): 포기 빈도·형태, meter↔feet 외 동일 패턴, 비율 메모 저장 후 중단 이유.
